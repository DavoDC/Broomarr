# Alternatives considered

Before investing further in Broomarr, this is the check that nothing else already does the job: read your Sonarr/Radarr library, work out from *watch history* what is genuinely safe to delete, and either recommend or delete it. Written 2026-09-14, as the top-priority backlog item that gated further feature work.

Broomarr's own differentiators, restated so the table below can be checked against them:

1. **True per-episode enumeration.** It reads Sonarr's actual episode list and takes a set difference against watched episode identifiers - never a count, never a percentage, never trusting a media server's own aggregate.
2. **Unknown blocks.** Anything that can't be established (unreachable API, missing timestamp, no history) is a reason *not* to delete, never a skipped condition that silently passes.
3. **Never deletes anything itself.** No delete API call, no filesystem access, ever - it prints a shortlist and a human deletes manually through Sonarr.

## Are these the right axes? (revisited 2026-09-14)

The first version of this table had an **"Auto-deletes?"** column, and treated a "Yes" in it as a strike. That framing does not survive contact with the actual library, where the media is re-downloadable. The column has been replaced with **"Wrong-call cost (reversal window)"**, for three reasons.

**"Does it delete?" is the wrong question; "what does a wrong call cost, and how long do you have to catch it?" is the right one.** Under the old column, Purgeomatic (cron, deletes whole series on one aggregate timestamp, no undo) and reaper (dry-run by default, off until armed, canary delete first, arm re-read before every item, manual spare, grace countdown) both scored "Yes." Those are not the same risk and the table was hiding that. The variable that actually matters is whether there is a window between the decision and the irreversible act, and whether anything is watching during it.

**Re-downloadability lowers the cost of a wrong deletion, but does not zero it, and the residue is not evenly spread.** For the common case - a readily available series - a wrong delete costs some time and bandwidth to reacquire, which is annoying rather than serious. Three things sit outside that: media that is genuinely hard to reacquire (out of print, an unusual cut, anything personal); the fact that a wrong deletion is usually noticed weeks later, when whoever wanted to watch it goes looking, so the cost includes the interruption rather than just the bytes; and the possibility of a *systematic* fault, where one bad run removes fifty shows rather than one. The first two argue for an exclusion list rather than a blanket read-only rule. The third argues for caps and a canary, which is exactly what reaper built.

**So: keep enumeration and unknown-blocks as axes - they are upstream of everything else - but stop treating them as the whole answer.** Classification rigour and recoverability are complements, not substitutes: rigour reduces how often you are wrong, recoverability reduces what it costs when you are, and a tool needs a defensible position on both. The argument that "recovery is cheap so classification can be sloppy" fails on the systematic-fault case, because cheap recovery per item is still expensive fifty times over, and on the noticing problem, because a recovery you never trigger is not a recovery. Broomarr's position is maximal on rigour and maximal on recoverability (it deletes nothing), which is a coherent but extreme corner; the question `docs/IDEAS.md` now carries is whether trading a little recoverability for a lot of convenience is worth it once the rigour has been demonstrated over time.

## Not this category (checked and ruled out on purpose)

## Correction: the premise of the first version of this section was wrong

The first version of this document, written from README claims only, argued that **every** competing tool asks the media server for watched status and that none claims Sonarr-side enumeration as ground truth. Reading the code disproves that for two of them.

**reaper reads Sonarr's episode list directly.** `season_scan.py` calls `client.episodes(seriesId)` per show and builds its denominator in `_final_episodes()` (L1039-1058) from `hasFile`. Its own docstring rejects `episodeCount` and `totalEpisodeCount` by name, for exactly the reasons `docs/References/DevContext.md` gives - `episodeCount` is download intent, `totalEpisodeCount` counts unaired episodes so a season could never read as finished. That argument was reached independently, in another language of the same problem, by someone who was not reading this repo. Broomarr's central architectural claim is therefore not unique, and this document should stop implying it is.

**Reclaimerr does the same thing** through `season.sonarr_episode_numbers` as the denominator, with the comment "Sonarr's canonical episode inventory is the denominator." It is a hybrid - Sonarr for the episode inventory, Plex for watch state - which is structurally the same shape as Broomarr's Sonarr + Tautulli join.

What survives the correction is narrower and more honest: Broomarr's differentiator is not *asking Sonarr*, it is the **set difference**. reaper compares two high-water marks (highest episode watched vs highest episode on disk) and relies on a separate, operator-disableable `protect_incomplete` gate to catch mid-season gaps. Reclaimerr matches per episode number but then reduces to `len(watched), len(expected)` at the boundary. Broomarr takes `on_disk_eps - watched_eps` and names the survivors. That is a genuinely stronger check, but it is one increment stronger than the field, not a different category from it.

## Why build, not fork

- **Data source is no longer the discriminator.** Maintainerr, Deleterr and Purgeomatic still fail on it; reaper and Reclaimerr do not. The discriminator that remains is the precision of the comparison (set difference vs high-water mark vs counts) and what a wrong call costs.
- **Deleterr is the one genuinely unsafe tool in the field**, and worth naming as such: "no watch record found" and "never watched" are the same value to it, so an empty or failed Tautulli fetch makes a whole library deletable under a common configuration. That is the exact skip-on-unknown failure `DevContext.md` describes, in its purest form.
- **reaper is not a weaker tool than Broomarr.** It is a considerably stronger one on every axis except comparison precision and legibility: 126 test files, 31 dated Alembic migrations that read as defensive schema evolution rather than churn, and an `executor.py` documenting eight independent pre-delete interlocks (approval and policy re-hash, manual spare re-check, caps that abort rather than truncate, a canary delete of the smallest item first, arm re-read before every item, streaming veto, played-since-approval re-check, size and existence re-read) behind *two* independent kill switches - an executor `dry_run` that defaults on and a host environment variable the web UI cannot reach. Its `gates.py` makes "a protection can delete a file" unrepresentable in the type system. This is more safety engineering than Broomarr has or is likely to acquire.

**Verdict: keep building Broomarr, but stop claiming it is the only tool that gets the data source right, and actually run reaper in dry-run mode against the real library before the next planning round.** The reasons not to fork are now practical rather than architectural:

1. **Licence.** reaper is AGPL-3.0; Broomarr is MIT. Forking relicenses Broomarr and every future addition to it. That is a deliberate decision, not a detail, and it is a poor trade for a tool whose value is that one person can read it end to end.
2. **There is nothing to harvest.** reaper's rigour is inseparable from its stack - a database, 31 migrations, a scan runner, an evidence layer, a policy engine, a React front end. You cannot take `_anchor_positions()` and leave the rest; it takes a `Mapping` that only reaper's scan pipeline produces. A "fork" here would in practice mean *adopting reaper and retiring Broomarr*, which is a different decision from forking and should be evaluated as one.
3. **They solve different-sized problems.** reaper is a multi-instance, policy-driven, web-administered deletion system with an arm switch. Broomarr is a script that prints a list. The second is not a worse version of the first; it is the appropriate size for one library and one reader, and its whole safety case is that a person can hold all of it in their head.

But the honest conclusion is that reaper is the first tool in this survey that is not disqualified on the merits. If David runs it dry against the real library and it produces a sane shortlist, the case for maintaining Broomarr narrows to "it is mine, it is one file, and its comparison is exact." Those are real reasons; they are not the same as "nothing else does this job."

**Adopt from reaper regardless of the fork decision:**

- **Keep "could not read" distinct from "read, and it was empty."** reaper carries `episodes_read` and `episodes_unreadable` flags alongside the episode map precisely so an empty map from a failed Sonarr call cannot be mistaken for a show with no episodes, and its `season_final_episode` is typed `Mapping | None` with a module docstring insisting "a missing episode map is `None`, never `{}`". Broomarr should audit `episode_facts()` for the same collapse - an exception path that yields an empty set of on-disk episodes would make `on_disk_eps - watched_eps` empty, which reads as "nothing unwatched," which is a pass. That is a fail-open hiding inside a fail-closed design, and it is worth a test.
- **Name the incomplete-season protection explicitly.** reaper surfaces "episodes are missing" as a reason string an operator sees. Broomarr's `explain()` should do the same rather than leaving it implicit in the verdict.
- **If auto-delete is ever built** (see `docs/IDEAS.md`), reaper's canary-first ordering and its arm-re-read-before-every-item are the design template, not something to reinvent.

**Fragility check.** Three things would change this verdict, in descending order of likelihood:

1. **A dry run of reaper against the real library produces a shortlist as good as Broomarr's.** This is testable this week and nobody has tested it. Until it is, "keep building" rests partly on an untested assumption.
2. **reaper ships a tagged release.** Today the only tag is `dev-build`, with commits through 2026-09-10. A stable release removes the last non-architectural objection.
3. **Broomarr's web UI (`docs/IDEAS.md`) gets built.** That is where the duplication becomes expensive - reaper already has a front end with an approval flow, and building a second one to reach parity is the point at which maintaining two tools stops paying. The CLI is cheap to keep; the UI is not.

## Source-verification notes (2026-09-14)

All seven candidate repos cloned and read at `--depth=1` (source only, no history). Findings below are from reading the actual code, not documentation claims.

### Audit of the enrichment pass (second reading, independent of the first)

Five citations were re-checked line by line against the clones. Four were exact: `season_pruning.py` L285-311, `gates.py` L20-22, `rule_engine.py` L3640-3671 and L2040-2082, `media_matcher.py` L105-106 all say what they were quoted as saying. Three corrections were needed, one of them material.

- **Path corrections (minor).** `gates.py` is `src/reaper/engine/gates.py`, not an unqualified `gates.py`. `unavailable_series_ids` lives in `backend/tasks/cleanup.py` (L1660-1676), not in `rule_engine.py` where it was cited. `media_matcher.py` is `prunarr/services/media_matcher.py`. All three now carry full paths.
- **Deleterr's cell was framed wrongly (moderate).** It described `watch_status` as a per-item state that could be "unset or unknown." It is a per-*library* configuration option taking `"watched"` or `"unwatched"`. The fail-open is real but sits one level down, in `find_watched_data()` (L2129-2145), which returns `None` indistinguishably for an unreachable Tautulli, an empty activity set, a failed GUID match, and a show nobody has watched. The corrected cell says that instead, and it is a sharper indictment than the original.
- **The material error: the enrichment pass established that reaper reads Sonarr's episode list, and did not notice that this falsifies the document's central argument.** `_final_episodes()` (`season_scan.py` L1039-1058) builds reaper's denominator from Sonarr's `/episode` response on `hasFile`, and its docstring rejects `episodeCount` and `totalEpisodeCount` by name for the same reasons `DevContext.md` does. The "Why build, not fork" section was at that moment still asserting that every tool asks the media server and that none claims Sonarr-side enumeration. Both halves of that were false and the evidence to see it was already in the notes. The section has been rewritten; the failure mode is worth naming - facts were gathered correctly and the conclusion they contradicted was left standing next to them.
- **Correction to the enrichment's own reading of reaper's precision.** The notes called reaper "episode-precise" without qualification. `_final_episodes()` returns the *highest on-disk episode number* per season and `_anchor_positions()` compares it to the viewer's *highest completed episode number*. Both sides are high-water marks, so the comparison cannot see a hole in the middle of a season; that case is caught by the separate `protect_incomplete` gate, which is the one protection an operator can switch off. reaper is more precise than the field and less precise than a set difference, and it is worth being exact about that since it is now the whole of Broomarr's remaining technical claim.
- **reaper's fail-closed behavior is stricter than "skip the one item with missing data": an unknown episode index protects *two* seasons** (the current one and the next), not just the one in question - `_anchor_positions()`'s `if final is None or watched is None: return {anchor} | _next_after(anchor, on_disk)`. Confirmed by its test `tests/test_season_pruning.py::test_an_unknown_watched_position_falls_back_to_season_level` (L287). Broomarr's own unknown-handling blocks the whole series, so there is no outward hedge to add - its unit is already the widest one. The transferable lesson is a different one: reaper keeps `episodes_read` separate from an empty map so a failed read cannot impersonate an empty library, and Broomarr should verify it does the same (see "Adopt from reaper" above).
- **reaper's maturity signal is the most surprising finding of this pass, and it holds up on re-check.** 126 test files, 31 dated Alembic migrations reading as defensive schema evolution rather than churn, and an `executor.py` whose module docstring alone enumerates eight pre-delete interlocks behind two independent kill switches. Latest commit 2026-09-10, PR numbers in the 990s. Still no version tag - the only tag is `dev-build` - so "pre-release" is literally accurate and badly misleading about the state of the code.
- **Deleterr is the one tool in this batch that is fail-open by default for the core "not watched" case.** See the corrected table cell above; this is the clearest real-world instance of the failure mode `DevContext.md` was written about.
- **Purgeomatic has no per-episode logic of any kind for TV** - it deletes or keeps entire series based on one aggregate `last_played` timestamp per show from Tautulli's library-info endpoint, with no Sonarr episode-API call anywhere in the watched-status path (Sonarr is only queried to find the series ID to delete, after the decision is already made).
- **OCDarr is architecturally different from the rest of the field** - it is not a periodic library sweep at all. It's a Plex/Jellyfin webhook listener that reacts to a single playback event and deletes previously-watched episodes behind the current playback position, per Sonarr episode ID. This makes its "per-episode enumeration" answer straightforwardly "yes," but it isn't solving quite the same problem Broomarr is (whole-library review) - worth noting for the next pass in case the table's framing needs a caveat for tools that operate on trigger events rather than scans.
